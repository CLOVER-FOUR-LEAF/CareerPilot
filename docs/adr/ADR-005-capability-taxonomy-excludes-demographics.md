# ADR-005 · 能力维度 taxonomy 不含人口学特征

- **状态**：已采纳
- **日期**：2026-10-22
- **相关**：计划书 §5.6、§3.3、§8.3 检查 C-4

## 背景

规则引擎按词表匹配，天然会放大文本里的统计相关性。
招聘场景里最敏感的几类信号 —— 性别、年龄、毕业年份、毕业院校、
专业、籍贯 —— 在简历文本里都可能出现。

它们的危险之处在于**相关性而非因果性**：
「某院校毕业」与「某类岗位表现好」在历史数据上相关，
但把「院校」当作能力信号，等于把历史偏见固化进模型。
 EEOC 与 NYC LL144 关注的正是 disparate impact，
而不是「模型有没有故意歧视」。

## 备选方案

| 方案 | 做法 | 问题 |
|---|---|---|
| A. 全维度建模 | 把学历、院校也作为能力维度 | 直接放大统计歧视 |
| B. 靠 prompt 回避 | 告诉模型不要用人口学特征 | 不可验证；而且这些特征根本不该进输入 |
| C. **在模型层排除** | taxonomy 不含人口学维度，且输入过滤 | 需要同时做输入过滤与输出校验 |

## 决策

采用 **C**，三条措施：

### 1. taxonomy 本身干净

`CAPABILITY_DIMENSIONS` 只有六个能力维度：
delivery / scale / architecture / data / domain / collaboration。
**没有**性别、年龄、毕业年份、毕业院校、专业、籍贯。

### 2. 输入过滤

归因层的输入只包含：JD 文本、简历文本、JD 硬技能、gap 列表。
**不含**用户档案（`birthYear` / `graduationYear` / `school` / `major`）。
用户档案在 `user-center` 里，与匹配链路完全隔离。

### 3. 学历门槛按「岗位要求」处理，而不是「能力证据」

这是最容易搞混的一点：

- 学历门槛**要识别**（JD 写了「本科及以上」就是准入条件），
  否则 HR 拿到的报告遗漏了硬性条件；
- 但学历门槛**不进入能力维度覆盖**，也**不作为「能力弱」的证据**。

实现上：硬门槛 gap 的 `gap_category = "hard_gate"`，
在 `build_capability_coverage()` 里被排除；
但它仍然会生成一道验证问题（问的是**实际情况**，不是能力评价）。

> 计划书 §5.6 B6 的原话：「学历门槛仍按 JD 硬性条件处理
> （这是岗位要求不是偏见），但不作为『能力弱』的证据」。

### 4. 「无证据」≠「不具备」

见 ADR-004。这条是偏见缓解里最关键的一条：
如果「简历没写」被当作「不具备」，那么简历写得越单薄的候选人
（往往是非正规教育路径的候选人）会被系统性低估。
三值枚举里的 `not_evidenced` 明确区分了这两件事。

## 代价

- 学历、年限这两类硬门槛无法进入「能力维度覆盖」图，
  报告里要单独分区展示，UI 复杂度上升。
- 过滤用户档案意味着 HR 无法基于「目标职级」调整提问深度 ——
  这在理想的产品形态里应该支持，但**不在本期**。

## 必须如实说明的边界

以上是**内部自检**，**不等于**通过 NYC Local Law 144 要求的
**独立第三方偏见审计**。要做真正的偏见评估，
需要外部审计机构用真实数据跑，这不在工程范围内。

## 什么条件下推翻它

不推翻。若未来要支持「按目标职级调整提问难度」，
应当引入**岗位层级**这一维度（如 P6/P7），
而不是把「候选人的毕业年份」当成信号 ——
前者是岗位属性，后者是人口学属性。
