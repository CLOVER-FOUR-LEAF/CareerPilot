# ADR-006 · 本期不改造 LangGraph 图结构

- **状态**：已采纳
- **日期**：2026-10-22
- **相关**：计划书 §5.1、§11.5（E1/E2 演进项）

## 背景

现有编排图是「taskType → 单节点」的一对一映射：

```
route ──> <业务节点> ──> finalize
```

它有两个已知的结构性缺陷：

1. **JD 被解析两次**：匹配链路是「解析 JD → 抽特征 → 匹配」，
   业务链路是「解析 JD → 抽特征 → 解析」—— 同一份 JD 走两条路，
   两边抽出来的技能集合可能不一致。
2. **没有真正的多 Agent 协作**：每个任务只调一个 Agent，
   没有 fan-out、没有反思循环、没有 checkpoint。

看起来应该先把图改成「解析 ∥ 抽取 → 对齐 → 评分 → 反思循环」。

## 备选方案

| 方案 | 做法 | 问题 |
|---|---|---|
| A. 先重构图，再做功能 | 先把 LangGraph 改造成协作图，再实现 HR 侧 | 图重构会拖慢所有功能；且重构期间无法验证功能是否正确 |
| B. **功能先行，图后重构** | HR 侧用现有图结构实现，图重构列为演进项 | 短期图结构不够优雅 |
| C. 两者并行 | 边做功能边改图 | 两件事互相干扰，出问题难定位 |

## 决策

采用 **B**。

本期在现有图上**只新增节点，不改结构**：

```
route ──> hr_insight ──> finalize
       ──> jd_calibrate ──> finalize
       ──> hr_verify ──> finalize
```

`should_continue()` 从字典查表，天然支持新增 taskType。
`NODE_HANDLERS` 加三个元组即可。

`hr_insight` 节点内部串起两步（match-agent → interview-agent），
但这是**编排**（决定谁先谁后），不是业务逻辑 ——
所有判定仍在 Agent 侧，编排层不含任何阈值、枚举或文案。

## 代价

- `hr_insight` 节点比其他节点长（两次下游调用），与其他节点风格不一致。
- 图结构里仍然没有并行与反思能力。
- 未来做 E1（JD 只解析一次放共享 state）时，
  `hr_insight` 节点需要跟着改。

## 什么条件下推翻它

出现以下任一情况就启动 E1/E2：

- 业务侧反馈「同一份 JD 在匹配页和 HR 页显示的技能列表不一致」；
- 需要多 Agent 互相校验（比如让 LLM 出题后再由规则复核）；
- 需要人在环路（面试官中途介入决定下一个问题方向）。

重构时的迁移路径已经预留好了：
`RESULT_KEYS` / `AGENT_NAMES` / `NODE_HANDLERS` 三张表是唯一的注册点，
新增 taskType 不需要碰图的其他部分。
