# ADR-001 · 确定性内核与 LLM 表现层分离

- **状态**：已采纳
- **日期**：2026-10-22
- **相关**：计划书 §3.5 约束 C3、§4.2、§5.3

## 背景

HR 侧能力要把「简历里的证据缺口」翻译成「面试官该怎么问」。
如果把判定整体交给 LLM，会出现三个问题：

1. **不可复现**：同一份输入两次跑出的结论可能不同，没法做回归基线，
   也没法向面试官解释「为什么这道题这么问」。
2. **不可审计**：结论一旦出错，无法定位是规则错了还是模型抽风了。
3. **合规风险**：受监管场景下，输出必须能说清楚「这个结论是怎么来的」。

## 备选方案

| 方案 | 做法 | 问题 |
|---|---|---|
| A. 全交给 LLM | 维度、层级、问题、判定全部由模型产出 | 不可复现、不可审计、幻觉风险高 |
| B. 全用规则 | 完全不调 LLM，模板硬编码 | 文案僵硬；规则覆盖不到的表达方式处理不了 |
| C. **内核规则 + 表现层 LLM** | 判定归规则，措辞归 LLM | 需要清晰划界，但两边都能做好自己的事 |

## 决策

采用 **C**。

具体边界：

| 产出 | 归属 | 理由 |
|---|---|---|
| `dimension`（能力维度） | 规则 | 确定性、可测试、可审计 |
| `required_level` / `evidence_level` | 规则 | 同上 |
| `gap_kind`（差距类型） | 规则 | 同上 |
| 问题的结构（意图 / 追问 / 判定信号） | 规则 | 保证「每个 severity≥4 的 gap 都有问题」这类硬指标 |
| 问题的**措辞** | LLM（可被拒绝） | 只有这里需要自然语言 |
| 判定的**枚举值** | 规则优先，LLM 兜底 | 兜底时必须有可校验的原文引用 |
| 报告的**免责声明** | 代码拼接 | 见 ADR-003 |

LLM 产出**一律要过代码校验**：
- 问题措辞要过 linter（四条硬规则），不过就丢弃、保留规则版本；
- 判定引用要能在原文里定位（见 ADR-002），不过就整条结论丢弃。

## 代价

- 规则要维护。维度 taxonomy、提问框架、特征词表都是人工维护的词表，
  换领域要重写。
- LLM 的「润色」价值有限 —— 规则生成的句子本来就可读。
  为了保持可复现，实际部署时也可以直接把温度设成 0 只跑规则路径。

## 什么条件下推翻它

如果出现下面的情况，说明划分方式需要调整：

- 规则维护成本超过 LLM 漂移成本（例如 taxonomy 要覆盖上百个垂直领域）；
- 业务上明确接受「每次结论略有不同」，且判定结果不要求可复现。

即便如此，**判定枚举与免责声明也仍应由代码控制** ——
那部分是合规要求，不因产品取舍而放宽。
